# 审查评分规则

评分只做轻量风险量化，不替代文字结论。

## 目标

- 让每次 review 都有一致的打分口径
- 优先体现严重程度和是否必须修复
- 简单、可解释，不做复杂模型

## 起始分

- 总分默认 `100`

## 扣分规则

按单条 finding 扣分：

| 严重程度 | `mustFix: true` | `mustFix: false` |
|---|---:|---:|
| `S1` | 40 | 25 |
| `S2` | 25 | 15 |
| `S3` | 12 | 6 |
| `S4` | 4 | 2 |

补充规则：
- 同一根因不要重复扣分；如果同类问题在多个文件重复出现，可以合并成一条 finding
- `questions` 不直接扣分，但如果待确认问题影响核心业务判断，结论应偏保守
- 分数最低为 `0`

## 风险等级

根据最终得分输出风险等级：

| 分数区间 | 风险等级 | 建议 |
|---|---|---|
| `90-100` | 低风险 | 可合入，关注验证缺口 |
| `75-89` | 中风险 | 建议修复后合入 |
| `50-74` | 高风险 | 不建议直接合入 |
| `0-49` | 严重风险 | 必须修复后再审 |

## Ready 结论建议

- 存在任意 `S1` 且 `mustFix: true`：`Ready: No`
- 存在 `S2` 且 `mustFix: true`，或总分低于 `75`：`Ready: With fixes`
- 无 must-fix 问题，且总分不低于 `90`：`Ready: Yes`
- 其他情况：结合问题集中度与验证缺口，在 `With fixes` 和 `Yes` 间判断

## HTML 报告中的展示项

HTML 报告至少展示：
- 总分
- 风险等级
- must-fix 问题数量
- 各严重程度问题数量
- `Ready` 结论

## 实施建议

- 评分只消费结构化 findings，不要从 markdown 文本二次解析
- 输出报告时同时展示“为什么是这个分数”，避免黑盒感
