# System Architect 技能重设计

> 日期：2026-05-27 | 版本：2.1 | 状态：待审批

## 1. Problem Statement

### 1.1 用户痛点

当前 system-architect 技能存在以下问题：

- **文档结构偏 CRUD**：四维度结构（应用/信息/集成/技术架构）偏向 REST API + 数据库场景，对 AI Agent、事件驱动、状态机等模式支持不足
- **缺少关键章节**：无技术选型对比、无代码库工程结构、无 Non-Goals、无迁移计划、无解决方案策略总览
- **非功能设计分散**：安全、高可用、性能、可观测性拆成 4 个平行维度，导致文档头重脚轻、重复描述、0→1 阶段写不动
- **深度不够**：当前技能虽然提到了深度要求，但产出仍偏"接口-only"，缺乏算法、状态机、数据 Schema、错误处理链等可实现细节
- **缺少 subagent 审查**：无自动化质量门控，依赖用户人工审查

### 1.2 痛点证据

参考 `docs/reference/arch.md` 中与 GPT 的讨论：
- 企业级架构文档的核心是"业务需求→技术方案"的映射，不是技术维度分类
- 安全/高可用/性能/可观测性本质都属于非功能设计，不应拆成大量并列章节
- 技术选型对比和代码库工程结构是"工程落地架构"的重要组成部分，但当前技能缺失
- 11 章结构比 Arc42 更适合中文企业级 0→1 项目

### 1.3 为什么现在做

- 已完成与 GPT 的架构文档结构讨论（arch.md）
- 已有 Arc42 方向的 spec（v1），但决定不采用 Arc42，改用 11 章结构
- PRD generation 技能已建立 subagent 审查模式，可复用

## 2. 设计目标

1. **文档结构贴近企业实践** — 11 章结构，非功能设计统一收敛
2. **技术选型有据** — 每个选型有对比表，说明为什么选、为什么不选
3. **全深度可实现** — 架构文档就是详细设计文档，每个组件都要深到可直接实现
4. **工程可落地** — 代码库与工程结构设计作为独立章节
5. **Subagent 先审 + 用户后审** — 参考 prd-generation 模式
6. **非功能设计具体可验证** — 不写模糊标签，写具体的设计决策和量化目标

## 3. 核心设计决策

### 3.1 文档模板：11 章结构

基于 arch.md 讨论的最终推荐结构：

| # | 章节 | 内容 | 对应原技能 | 变化 |
|---|------|------|-----------|------|
| 1 | 文档概述 | 目的、简介、名词解释、参考文档 | 概述 | 新增名词解释、参考文档 |
| 2 | 业务背景与系统目标 | 背景、目标、MVP 范围、**Non-Goals** | 概述 | Non-Goals 新增 |
| 3 | **技术选型与架构决策** | 选型原则、模式对比表、技术对比表、ADR 汇总、技术风险评估 | 分散在各维度 | **独立章节**，强化对比 |
| 4 | 总体架构设计 | 架构原则、C4 图、核心链路 | 应用架构 §2.1-2.5 | 核心链路错误路径从可选升级为必须 |
| 5 | 模块设计 | 每个模块：职责/不做什么/核心能力/关键方法/伪代码/状态机 | 应用架构 §2.3-2.4 | 要求全深度 |
| 6 | 数据与存储设计 | ER 图、Schema 样本、存储选型、数据流转、一致性 | 信息架构 | Schema 样本必须，存储选型增加对比 |
| 7 | 接口与通信设计 | API 规范、通信模式、事件清单、外部集成、错误映射链 | 集成架构 | 可简化（无外部依赖时） |
| 8 | **代码库与工程结构设计** | 仓库策略、目录结构、分层、依赖约束、工程规范 | **新增** | arch.md 明确要求 |
| 9 | 非功能设计 | 可用性/性能/安全/可观测性 | 分散在技术架构 | **统一收敛**，要求具体设计决策 |
| 10 | 部署与运维设计 | 环境、部署架构、CI/CD、配置管理 | 技术架构 §5.2 | 可简化（单进程时） |
| 11 | 风险与架构演进 | 风险登记、演进路线、**迁移计划** | 风险登记 | 新增演进路线和迁移计划 |

**章节简化规则：**

| 章节 | 何时可简化 | 何时必须写 |
|------|-----------|-----------|
| 7 接口与通信设计 | 无外部依赖时 | 有外部系统集成时 |
| 10 部署与运维设计 | 单进程插件/库 | 有部署选择时 |

其余章节永远必须。

### 3.2 全深度可实现

架构文档就是详细设计文档。不存在"浅层描述"的区域——每个组件、每个模块、每个接口都必须深到开发者可以直接据此实现。

**统一深度要求：**

| 元素 | 必须达到的深度 |
|------|--------------|
| 组件/模块 | 职责 + 关键方法 + 不做什么 + 伪代码（非平凡逻辑）+ 状态机（有状态组件） |
| API 契约 | 接口 + 错误类型 + 1 个使用示例 |
| 状态机 | 状态 + 触发条件 + 守卫条件 + 副作用 |
| 交互序列 | happy path + ≥1 错误/降级路径 |
| 算法 | 伪代码或逐步流程 |
| 数据 Schema | 每个持久化数据的 JSON/YAML 样本 |
| 技术选型 | 选定方案 + 备选方案 + 选型理由 + 风险 |
| 错误处理 | 外部错误 → 内部错误 → 调用方可见错误（完整映射链） |
| 非功能设计 | 具体的设计决策 + 量化目标，不是模糊标签 |

### 3.3 Subagent 审查机制

#### architecture-researcher

- **派发时机：** Step 4 行业调研
- **输入：** PRD 核心技术挑战
- **输出：** 2-3 个业界模式的研究摘要
- **归宿：** 不产出独立文档，织入架构文档各章节

#### architecture-reviewer

- **派发时机：** Step 8 架构文档写完后
- **审查态度：** 不信任声明，逐行验证内容
- **审查维度：** 章节完整性、可实现性、错误路径、Anti-Patterns、一致性、追溯性
- **输出：** Status: Approved / Issues Found + 具体问题
- **循环规则：** Issues Found → 修复 → 重新审查，直到 Approved

### 3.4 Anti-Patterns 检测清单

从 SKILL.md 拆出为独立 reference 文件，reviewer 也使用：

| Anti-Pattern | 症状 | 检测方法 |
|-------------|------|---------|
| 接口-only | 组件只有接口签名 | 检查是否有算法/伪代码/状态机 |
| Happy-path-only | 序列图只有成功流 | 检查每个序列是否有错误分支 |
| 标签-only 组件 | 组件名无职责描述 | 检查是否有"做什么/不做什么" |
| 状态机无触发 | "running → done" 无触发条件 | 检查每个状态转换是否有触发条件 |
| 扩展点无示例 | "用策略模式" 无接口签名 | 检查是否有接口 + 1 个实现示例 |
| Schema-less 数据 | "存为 JSON" 无字段 | 检查每个持久化数据是否有 Schema |
| 质量标签化 | "高性能" 无具体设计 | 检查非功能设计是否有具体机制和量化目标 |
| 缺少 Non-Goals | 无"不做的事" | 检查 Non-Goals 是否存在且非空 |

## 5. 流程详述

### Step 1: 确认 PRD 就绪

验证 PRD 已通过用户审批，获取文档路径。

### Step 2: 上下文摄取

- 读取 PRD，提取功能需求、非功能需求、约束
- 识别关键质量属性，按优先级排序
- 建立需求-架构追溯矩阵（PRD 需求 → 架构章节 → 设计元素）
- 澄清歧义（一次一问）

### Step 3: 行业调研

- 派发 architecture-researcher subagent
- 输出 2-3 个业界模式研究摘要
- 研究成果织入架构文档各章节

### Step 4: 解决方案策略

- 产出 3-5 句核心架构决策总览
- **向用户确认**：方案策略方向是否正确？

### Step 5: 按章节设计

按 11 章顺序设计，所有章节都要求全深度。每章完成后验证：本章是否覆盖了追溯矩阵中映射的 PRD 需求？

### Step 6: 可实现性门控

对每个组件回答：能实现？能测试？能调试？能扩展？

### Step 7: 写架构文档

保存到 `docs/<project>/YYYY-MM-DD-<project>-architecture.md`

### Step 8: Architecture Reviewer 审查

派发 reviewer subagent，循环修复直到 Status: Approved。

### Step 9: 用户审阅

交给用户审阅。修改后重新 Step 8-9。

## 7. 与 prd-generation 的衔接

prd-generation SKILL.md 中的 HARD-GATE：
> PRD 未获用户审批前，不得调用 system-architect 或进入架构设计阶段。

system-architect SKILL.md 中的 HARD-GATE：
> NO ARCHITECTURE WITHOUT A VALIDATED PRD.

衔接点：
- system-architect Step 1 确认 PRD 就绪，引用 `docs/<project>/YYYY-MM-DD-<project>-prd.md`
- 追溯矩阵（附录 A）建立 PRD 需求 → 架构元素的映射

## 8. 不做的事

| 不做 | 原因 |
|------|------|
| 采用 Arc42 模板 | 用户选择 11 章结构，更适合中文企业级 0→1 项目 |
| 风险驱动深度（🔴🟡🟢） | 架构文档就是详细设计文档，每个组件都要全深度，不存在"浅层区域" |
| QAS / Utility Tree | 非功能设计直接写具体设计决策和量化目标，不需要形式化场景模板 |
| 支持 TOGAF ADM 全流程 | 过于重型 |
| 合并 system-architect 和 prd-generation | 职责不同（What vs How） |
| 为每个章节拆分独立 reference 文件 | 过于碎片化，合并为 architecture-guide.md |

## 9. 成功指标

| 指标 | 目标 | 验证方式 |
|------|------|---------|
| 架构文档可实现率 | 每个组件可通过文档独立实现 | reviewer 审查无 Blocker |
| 全深度覆盖 | 每个组件达到深度要求表的标准 | reviewer 检查 |
| 错误路径覆盖 | 核心链路每个序列 ≥1 错误路径 | reviewer 检查 |
| 非功能设计具体性 | 非功能设计有具体机制和量化目标，无模糊标签 | reviewer 检查 |
| 章节完整性 | 必须章节 100% 存在 | reviewer 检查 |
| Subagent 审查通过率 | ≤2 轮修复即通过 | 迭代次数统计 |
